## 1. Research Context & Objectives

### 1.1 Problem Formulation
Pedestrian trajectory prediction requires modeling the inherent multi-modality and indeterminacy of human motion. Traditional stochastic predictors typically map a single latent variable $z \sim \mathcal{N}(0, I)$ via a generative adversarial network (GAN) or conditional variational autoencoder (CVAE). 

### 1.2 Motion Indeterminacy Diffusion (MID)
MID (Gu et al., CVPR 2022) formulates trajectory forecasting as a reverse process of a parameterized Markov chain (Denoising Diffusion Probabilistic Model — DDPM):
1. **Forward Process**: Gradually adds Gaussian noise to the true future trajectory over $T$ diffusion steps (default $T=100$), transforming structured human motion into an isotropic Gaussian distribution over the walkable space.
2. **Reverse Process**: Progressively removes indeterminacy conditioned on historical trajectory states and social interaction embeddings generated by a Transformer/RNN spatial-temporal encoder.
3. **DDIM Acceleration (04/2023 update)**: Introduces non-Markovian Denoising Diffusion Implicit Models (DDIM) to reduce reverse sampling to 2 to 5 steps for faster inference (~50× acceleration).

## 2. Official Implementation Audit (`research/MID/`)

### 2.1 Repository Layout
- `main.py`: Entry point for training and evaluation.
- `mid.py`: Core `MID` class orchestrating model training, evaluation, checkpointing, and logging.
- `models/`: Autoencoder, Trajectron++ spatial-temporal encoder, Transformer diffusion network (`models/diffusion.py`).
- `configs/baseline.yaml`: Hyperparameter specifications.
- `process_data.py`: Data conversion script transforming raw ETH/UCY `.txt` files into pickled `Environment` objects (`dill`).
- `env/mid_env.yaml`: Official Conda environment definition.

### 2.2 Input & Output Conventions
- **Observation Window ($T_{obs}$)**: 8 timesteps (3.2 seconds at 2.5 Hz / $dt = 0.4$ s).
- **Prediction Horizon ($T_{pred}$)**: 12 timesteps (4.8 seconds at 2.5 Hz / $dt = 0.4$ s).
- **Coordinate System**: World-frame 2D Cartesian coordinates in meters, mean-centered per scene.
- **Sampling Interval**: $dt = 0.4$ s (downsampled from 25 fps video by a factor of 10).
- **Output Tensor**: $B \times K \times 12 \times 2$, where $B$ is batch size (number of agents), $K$ is number of stochastic samples (default $K=20$), predicting 12 future $(x, y)$ coordinate pairs.

   - `mid.py` line 236: `self.registrar = ModelRegistrar(self.model_dir, "cuda")` hardcodes `"cuda"`. On our machine without an NVIDIA GPU, this raises a PyTorch runtime error.

## 5. Feasibility Verdict & Strategic Direction

### 5.1 Verdict
- **Unmodified Gutianpei/MID Repository**: **No-Go**. Cannot run inference due to absent weights, uninstalled legacy dependencies, hardcoded CUDA requirements, and script errors.
- **Scientific Concepts from MID**: **Viable for Future Adaptation**. The diffusion framework, state embeddings, and multi-modal trajectory generation are conceptually sound, but wholesale copying of the repository is unmaintainable and unnecessary.

### 5.2 Recommended Direction for GenEvac-Sentinel
1. **Part 1 Decision**: Adopt a **Conditional Go** posture for Module B planning.
2. **Architecture Decoupling**: Do not embed `research/MID` in `src/genevac`. Keep research materials strictly quarantined under `research/`.
3. **Inference Strategy**:
   - **Primary Baseline**: Implement a pure kinematic constant-velocity baseline predictor using only historical trajectory points (explicitly decoupling trajectory prediction from movement planning).
   - **Learned Model**: Develop a clean, lightweight PyTorch-based model (e.g., GRU/TCN Trajectory Predictor) natively designed for Python 3.10+, CPU inference, and 0.1s simulation timesteps.
4. **Empirical Latency Findings**:
   - Pure Kinematic Baseline: $0.14\text{ ms}$ for 50 agents on host CPU.
   - Lightweight Neural Predictor (GRU): $10.11\text{ ms}$ total ($9.84\text{ ms}$ forward pass + $0.27\text{ ms}$ tensor conversion) for 50 agents on host CPU.
   - Simulation frame budget must be formally confirmed with Person A rather than assumed.
5. **Person A Contract**: Establish a clean, read-only interface contract with Person A before implementing Part 2.
